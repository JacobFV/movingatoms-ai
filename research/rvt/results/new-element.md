# Fresh DataStorage payload and creation identity

The bounded experiment constructs the three bodies of a new non-geometric
`DataStorage` element from named values and the file's embedded schema. It does
not clone source body bytes or reuse another element's identity. **No complete
RVT save or Autodesk acceptance is claimed.**

The [six-file inventory](new-element-inventory.json) finds a complete DataStorage
sample in pinned MIT `core2024.rvt`, element 80437. Most smaller objects are
singleton document settings, making them poor duplication targets. Rooms carry
level/boundary references. DataStorage's actual sample has only self/unset
ElementId references and two existing file-local Extensible Storage schemas:
`FDXModifiedExchangeList` (empty string) and `DataStorageUniqueId` (GUID).

`new_element.py` encodes a fail-closed subset of the embedded field descriptors:
by-value classes, inheritance, counted arrays, deferred pointers, class tags,
UTF-16 strings, GUIDs, booleans and signed integers. Field names must match the
schema exactly; unknown flags and descriptor forms are rejected. The entry point
is restricted to the measured 2024 class profile and validates both ES schema
names and field declarations. It intentionally preserves the observed DataStorage
header flag values; their creation semantics remain unproven.

Re-encoding the source model from named values reproduces all three original
bodies exactly (119, 217, 2 bytes). New element 133210 is allocated above
IdentifierSource.m_last, with an independently assigned ES GUID and name
`Clean-room DataStorage Δ`. Independent public-reader decoding consumes all
119/265/2 generated bytes and returns 2/5/1 objects and 1/4/0 resolved edges.
Every decoded ElementId reference is -1 or 133210; the body self-ID and header
self-deletion reference both use the fresh ID. The new storage GUID is absent
from the independently decoded current DataStorage GUID inventory.

The 40-byte ElemRec sets creation, modification and user-modification episodes
to 39, matching the equal-date pattern in the source newly-created DataStorage.
A new History episode is prepended using the existing guarded codec.
Independent native-index parsing finds 26,426 identities, preserves all 26,425
old identities exactly, and derives the new UniqueId:
`562a3df0-6022-5912-aeb1-33b6a875b44e-0002085a`.

The generated records also round-trip through the experimental unsigned
partition builder. The report binds the fixture SHA, public reader revision,
embedded schema SHA, body hashes, graphs and all reference paths.

Remaining boundaries:

- The encoder depends on the two existing file-local ES schemas; it does not
  invent or register an ES schema in an arbitrary document.
- A separate registration audit below verifies the three measured incoming
  Global/Latest references; broader native creation rules remain unproven.
- It does not emit a whole RVT, synchronize save metadata, solve signatures or
  demonstrate Revit acceptance. Core's existing 66 increments and latest episode 38
  suggest partition 66 / episode 39 for a subsequent explicit append experiment.
- Caller-supplied IDs/GUIDs require document-wide allocation/collision checks when
  integrated. This experiment checks the source allocator, History uniqueness
  and current DataStorage ES GUIDs; it is not a general global UUID registry.

## Reproduce

```sh
python3 research/rvt/new_element_experiment.py \
  --reader-source /path/to/pinned/rvt-rs \
  --target research/rvt/local/new-element-build/target \
  research/rvt/local/core2024.rvt \
  --result research/rvt/results/new-element.json \
  --profile research/rvt/results/new-element-profile.json
python3 -m unittest discover -s research/rvt -p test_new_element.py
```

Nine payload/registration regression tests pass. Evidence is in [new-element.json](new-element.json);
[the compact schema profile](new-element-profile.json) supports offline tests.
The independent Rust helper is built in ignored scratch storage against the
pinned clean public reader; no Revit code or proprietary SDK is read.

## Incoming registration audit and actual candidate

Complete independent decoding of source Global/Latest finds three incoming
references to source DataStorage 80437: the `-100` list in
`ElemsSetWithCellsTracking.m_elemIdSetMap`, plus each of the two schema-specific
`EStorageTracking.m_trackingItems` ID sets. An ElemTable-only insertion would
leave these registrations incomplete.

`new_element_registration.py` appends 133210 to those three lists using independently
decoded field spans, exact inflated-source SHA, verified counts, sorted unique IDs
and non-overlapping replacement spans. Global/Latest grows by 24 bytes. A complete
re-decode preserves 252 objects and 251 pointer edges. The entire semantic graph
is identical except for the three expected ID insertions; position offsets move
because the arrays grow.

The same check was run against the actual registered candidate produced by the
separate append-save experiment, SHA
`99dcd64c7d5a881e4cdbc8bf202b05f9abaf85e06917967c0cb5ddab19de5936`.
Its actual Global/Latest payload matches the guarded expected output exactly.
This establishes measured registration consistency, not every possible
DataStorage creation rule or Autodesk acceptance. See
[new-element-registration.json](new-element-registration.json).

```sh
python3 research/rvt/new_element_registration.py \
  --reader-source /path/to/pinned/rvt-rs \
  --target research/rvt/local/new-element-build/target \
  research/rvt/local/core2024.rvt \
  --candidate research/rvt/local/create-candidate-registered.rvt \
  --result research/rvt/results/new-element-registration.json
python3 -m unittest discover -s research/rvt -p 'test_new_element*.py'
```
