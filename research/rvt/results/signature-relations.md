# Signature relationships in source content groups

Date: 2026-10-22. Two file-only probes analyze all six pinned MIT fixtures.
Source SHA-256 values are in [signature-relations.json](signature-relations.json)
and [signature-relations-schema.json](signature-relations-schema.json). The
schema helper invokes the public clean-room `rvt-schema` binary, recording its
hash and version; it does not inspect Revit or ODA binaries.

## Same content key does not imply interchangeable serialized content

Four content GUIDs occur in both RE1-Mechanical (`Partitions/78`) and
RE1-Plumbing (`Partitions/61`). They form especially useful near-matching source
pairs. The following comparisons exclude terminal records; record position is
used only for describing observed correspondence, not as proof of identity.

| Mechanical/Plumbing group | Records each | Equal IDs at record position | Equal 101 bodies | Equal 102 bodies | Equal 103 bodies |
| --- | ---: | ---: | ---: | ---: | ---: |
| 18 / 22 | 213 | 212 | 211 | 211 | 213 |
| 24 / 23 | 719 | 717 | 716 | 716 | 719 |
| 30 / 32 | 590 | 588 | 587 | 587 | 590 |
| 31 / 33 | 213 | 212 | 211 | 211 | 213 |

All four pairs have different 64-byte private fields. Their complete inflated
bytes differ, as do each of the three channels when record IDs are included.
The differing ID offsets are listed in the machine-readable report. No global
constant ID translation explains these pairs: almost all IDs are unchanged.

This is actionable for content-document handling: **a ContentKey GUID alone
cannot safely key a cache of exact serialized group bytes or its private field.**
The same GUID is present with altered IDs and altered 101/102 bodies. The
sequence-103 body lists, with lengths but without IDs, are exactly equal in
each pair. A deterministic private field computed solely from the GUID, or
solely from these 103 bodies, cannot explain the observed fields. This leaves
other coverage, contextual inputs and nondeterministic algorithms open.

The original public text is identical for all 521 nonempty private fields:
`Data generated by Autodesk® Revit®`. The two empty private fields have empty
public text and zero declared elements. Public text alone therefore cannot
explain the private field as a deterministic function. No source example
supports nonempty unsigned content.

## Retained base-group overlaps

Within individual source files, 27 pairs of base groups share at least one
nonterminal object ID. Across these pairwise comparisons there are 1,788
shared-ID occurrences (not 1,788 distinct objects). Bodies match in 1,098 cases
for sequence 101, 1,137 for sequence 102 and 1,197 for sequence 103. Every pair
has different private fields, but every pair also has different complete
content. No signature determinism conclusion follows. The probe deliberately
does not infer episode order from partition names.

There are no repeated complete inflated groups or complete individual-channel
byte lists among the 521 nonempty groups. Consequently a controlled
same-message/different-signature test is still unavailable. Near-identical
content pairs above provide narrower inputs for future object-difference work,
not a solution to signature generation.

## Embedded schema inventory

Searching parsed class and field names for `signatur`, `crypt`, `sha256`,
`sha512`, `ecdsa`, and `ed25519` returns only `SignatureMarker` and its
`m_privateSignature` / `m_publicSignature` declarations in all six files. The
best-effort reader describes a container with no nested declarations and a
string. No class named `SignatureMaker` is present among those parsed results.
Previously verified ordinal metadata identifies `SignatureMarker` serialization
version 1 across the three year profiles; that is not a crypto algorithm ID.

This bounded name search does not establish absence of algorithm hints in
unparsed fields, opaque data or other representations. Guessed field types are
not treated as a wire specification. No keying or Autodesk enforcement claim
is made.
